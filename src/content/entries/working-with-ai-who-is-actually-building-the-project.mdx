I asked ChatGPT a question that has been sitting in the back of my mind for a while:

**When I build projects with AI, how much of the project is actually mine, and how much belongs to the AI?**

Across the projects we've worked on together, the answer was more nuanced than simply counting who wrote the code.

ChatGPT's overall estimate was:

> **About 65% me / 35% ChatGPT.**

That percentage changes considerably depending on what is actually being measured.

| Dimension | Me | ChatGPT |
|---|---:|---:|
| Project conception / reason for existing | **95%** | 5% |
| Requirements and priorities | **85%** | 15% |
| Product/design judgment | **80%** | 20% |
| Domain knowledge and real-world context | **90%** | 10% |
| Architecture / technical approach | 55% | **45%** |
| Coding and implementation | 30% | **70%** |
| Debugging and diagnosis | 45% | **55%** |
| Documentation / formalization | 35% | **65%** |
| Testing and real-world validation | **75%** | 25% |
| Iteration / refinement | **60%** | 40% |

## Lines of Code Are a Bad Measure

If contribution were measured by lines of code, AI would receive a much larger percentage.

That would also be misleading.

On a project like this website, ChatGPT may generate a substantial percentage of the React, Astro, TinaCMS configuration, documentation, migration logic, debugging changes, and other implementation details.

But that code exists inside a system whose behavior is still largely dictated by me.

I am usually the one making decisions such as:

- This editor workflow is wrong.
- The gallery needs to behave differently.
- This navigation structure doesn't make sense.
- Publishing should automatically trigger this process.
- This abstraction makes the system unnecessarily confusing.
- This needs to work properly on mobile.
- This technically works, but it isn't solving the problem.

Those decisions often have more impact on the project than an individual code change.

## Testing Against Reality

One of the largest parts of my contribution is something AI cannot easily substitute for: actually using the system.

I deploy it.

I use it.

I find the places where the intended design and the real implementation diverge.

That might mean discovering that selecting an Immich album behaves like running a search, that a preview window doesn't wrap text correctly, that a draft article is still publicly visible, or that a build pipeline behaves differently than expected.

Those aren't theoretical problems.

They appear because the software has left the planning stage and encountered reality.

The specification then changes based on what happened.

## The Job Search Project Is an Even Better Example

The job-search automation project makes the distinction particularly obvious.

AI can build:

- Job collectors
- Ranking algorithms
- Data schemas
- Scoring systems
- Local-model workflows
- Automation
- Documentation

But the hardest part of the system isn't necessarily the Python.

The difficult intellectual property is answering the question:

**What actually constitutes a good job for me?**

An early version of the system returned plenty of technically valid results. The problem was that the jobs weren't especially good matches.

Rejecting those results wasn't simply identifying a software bug.

It was supplying knowledge the system didn't possess.

The scoring model was failing to represent human judgment accurately.

Improving the project therefore meant encoding more of that judgment into the system.

## The Division of Labor

The simplest description of the relationship is probably this:

> **I tend to contribute the "why" and the boundary conditions. AI contributes a large portion of the "how."**

That distinction is becoming less absolute over time.

As I've worked on these systems, I've also become increasingly involved in the technical architecture: Astro, TinaCMS, GitHub, Cloudflare, Immich, Docker, R2, CI/CD, deployment workflows, branch management, and the interactions between them.

That means the process doesn't feel much like:

**Customer tells programmer what to build.**

It feels closer to:

**A project owner and an extremely fast engineering collaborator iterating on a system together.**

AI can traverse unfamiliar APIs, inspect codebases, propose implementations, produce documentation, and test hypotheses much faster than I could independently.

I can determine whether the resulting system actually makes sense.

## Intellectual Contribution vs. Production Labor

Breaking the percentages into two different categories makes the relationship clearer.

### Intellectual and Product Contribution

**75–85% me**

**15–25% AI**

This includes:

- Why the project exists
- What problem it should solve
- Requirements
- Priorities
- Constraints
- Product judgment
- Domain expertise
- Acceptance or rejection of solutions

### Implementation and Production Effort

**Approximately 40% me**

**Approximately 60% AI**

This includes:

- Writing code
- Refactoring
- Documentation
- Configuration
- Debugging
- Research
- Generating implementation alternatives

Those numbers aren't contradictory.

They show the leverage.

I am getting a substantial amount of production labor from AI without outsourcing ownership of the project itself.

## So Who Built It?

Someone looking at the Git history could reasonably say:

**AI wrote a lot of this code.**

That would be true.

But a different set of questions produces a different answer:

Who understands what the project is supposed to accomplish?

Who recognizes when the implementation is wrong?

Who decides what tradeoffs are acceptable?

Who determines what gets removed, changed, or rebuilt?

Who could continue directing development?

The answer to those questions is overwhelmingly me.

So the description that feels most accurate is:

> **I built these projects with substantial AI-assisted engineering.**

AI isn't merely autocomplete in this process. It contributes architecture, implementation ideas, debugging, code, research, and occasionally directions I hadn't considered.

But without continued human judgment, the projects would eventually become technically plausible implementations of the wrong thing.

And that may be the most important distinction.

**AI probably typed more of the production code. I supplied considerably more of what makes that code worth having.**
